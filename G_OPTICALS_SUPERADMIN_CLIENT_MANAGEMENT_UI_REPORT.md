# G OPTICALS ERP — Super Admin, Client Management & UI Size Report

Date: 2026-11-13 · Scope: cloud multi-tenant edition (Super Admin / Client Management) and the shared frontend (UI density) · Status: **implemented and tested. Not committed, not deployed, nothing installed.**

Nothing was run against production or the dev database "G OPTICALS". All browser testing used a throwaway database (`gopt_e2e_cm`), which was dropped afterwards. Backend tests used Django's own test database.

---

## 1. Why Super Admin sign-in / Client Management was failing

For a correctly provisioned platform owner, the cloud code path worked: the existing tests, a fresh database and a real browser all confirmed it. The failures came from four places around that path:

| # | Root cause | Effect | Fix |
|---|---|---|---|
| 1 | **Provisioning gap in `bootstrap_admin`.** If the configured `DJANGO_SUPERUSER_USERNAME` already existed but was not the platform owner, the command printed "already exists — nothing to do". This happens when the account is a tenant-#1 user without `is_superuser` (for example after the Oct-30 `DATABASE_URL` swap) or a client's user. Client Management requires `is_superuser` **and** tenant #1 (`is_platform_owner`). | The account could sign in but saw no Client Management link, and `/api/superadmin/*` answered 403. Nothing explained why. | `bootstrap_admin` now names the exact problem. `--reset-password` restores a tenant-#1 account. It **refuses** to promote another client's user. New read-only `manage.py platform_admin_status` lists every candidate account and why it can or cannot open Client Management. |
| 2 | **Portal confusion.** `/#/super-admin/login` admitted any role `SUPER_ADMIN`, and every client's own owner has that role. | A client owner using the "Super Admin" page landed on a normal dashboard with no Client Management, which looks exactly like "Super Admin can't access Client Management". | The portal sends `portal=platform`. The **server** refuses non-platform-owners before any token or 2FA challenge (403 `not_platform_admin`), with a message pointing to the main login. The platform owner now lands directly on Client Management. |
| 3 | **Hardcoded default credential.** With `DEBUG` on, `bootstrap_admin` silently created `superadmin` / `superadmin321`. | Violates the brief. A deployment left on `DEBUG` would expose a known platform-owner login. | Removed. No default account exists in any mode; the owner comes only from `DJANGO_SUPERUSER_*` or `createsuperuser`. |
| 4 | **Windows edition by design.** The installer's administrator is the customer company's `SUPER_ADMIN`, never a platform owner. | Client Management does not exist on a Windows install, and should not. | Kept as designed. The Windows `/super-admin/login` path now shows the normal sign-in. That edition manages its companies under **Organization → Companies**. |

Also fixed on the way:
- A refused portal sign-in raised a duplicate red global toast that stayed on screen after the next successful login. Sign-in calls are now `__silentError`; the page shows the error inline.
- The platform summary counted tenant #1 in "Active" but not in "Clients".

## 2. Client creation workflow

**Client Management → New client** opens a 5-step wizard. Nothing is saved until **Create client**. Then one `POST /api/superadmin/tenants/` creates everything in **one transaction** through the existing `onboard_tenant` service, so a failure leaves nothing half-created.

| Step | Fields | Stored in |
|---|---|---|
| Client | Client/Organization name\*, Owner name, Email, Phone, Country, Address, Tax registration (label follows the country: GSTIN/TRN/VAT No…), Logo (PNG/JPG/SVG) | `Tenant.owner_name/country/address/contact_*`; tax number → `Company.gstin`; logo → `BillingSettings.logo_data_url` (prints on bills) |
| Company | Company name, Registration no., Business address, Currency, Language, Time zone, Tax on/off | `Company` (name, business_reg_no, address, country, currency symbol, fiscal year from the country) + Business & Localization preferences |
| Main branch | Name, Address, Phone, Email | The default branch (plus its warehouse, created as before) |
| Administrator | Admin name, Username\*, and either a **password** or a **setup link (invitation)** | `User` role `SUPER_ADMIN` in the new tenant only. Never `is_superuser`/`is_staff`. |
| Modules & Subscription | Package / module switches, plan, start, expiry, max users, max branches | `Tenant` |

- **Tenant identifier**: generated by the server (numeric ID plus a unique slug code), shown as "Tenant ID #N (code)".
- **Country-driven defaults**: picking a country pre-fills currency, language and time zone. Choices the admin makes explicitly are never overwritten.
- **Invitation**: `apps/common/invitations.py` creates a one-time, 72-hour setup link. It uses Django's token machinery with its own salt, so a password-reset token cannot be used as an invitation. It stops working once used.
  - The token is never in the create response. The console fetches it from `…/users/<id>/invitation/`, and that response is marked so the idempotency cache **never stores it** (`Cache-Control: no-store`).
  - The admin opens `#/accept-invite`, chooses a password (Django validators apply) and signs in normally.
  - "Setup pending" shows in the Users tab, and new links can be issued per user. No e-mail is sent because there is no mail integration; the platform admin copies the link.
- **Editing**: the client's Overview tab edits profile, country, address, plan, dates, seats and branch limit. The other tabs (Modules & Permissions, Users, Branches, Data & Audit, Backups, History) are unchanged.

## 3. Module and subscription assignment

- **Modules**: unchanged rules in `module_access.py` (packages or custom toggles, one accounting tier, per-role levels).
- **Subscription** (new, migration `common 0012`, additive): `subscription_plan` (Trial, Monthly, Quarterly, Half-yearly, Annual, Perpetual), `subscription_starts_on`, `subscription_expires_on`, `max_branches`.
  - Existing clients get **Perpetual, no dates, no branch limit**, so nobody's access changes on migration.
  - Validation: term plans need an end date. Perpetual has none, and switching to it clears the date. The end date cannot precede the start date. The platform account cannot be given subscription terms.
- **Status** (derived): Deactivated → Subscription expired → Deactivation scheduled → Trial → Active.
- **Enforcement**:
  - **Expiry**: folded into `Tenant.active_q()` / `is_effectively_active`. The expiry day itself is still usable. From the next day, sign-in is refused with `subscription_expired` ("ended on …, contact your software provider"), and **open sessions are refused on their next request** (middleware). Renewing the date restores access immediately.
  - **Seats**: existing seat limit, unchanged.
  - **Branches**: new `check_branch_available()`, applied when the console adds or reactivates a branch **and** when the client creates, activates or re-enables a branch itself (403 `branch_limit`). Lowering the limit below the number in use is refused.
- **Suspend / activate**: the existing deactivate (reasoned, optionally scheduled) and reactivate flows, now offered for Trial and Expired clients too.
- **No payments, no licence keys** were added. The platform admin records the agreed terms.

**Client Management dashboard:**
- Summary tiles (clickable filters): clients, active, trial, expiring ≤ 30 days, expired/deactivated, active users, active branches.
- Columns: Tenant ID, client and owner, company, country, plan and package, active modules, users/limit, branches/limit, status, expiry, actions.
- Server-side search (name, ID, code, owner, email, phone, admin username), filters (status, plan, country, expiring) and pagination (`?page=&page_size=`; without `page` the endpoint still returns the plain list older callers use).

## 4. Tenant isolation verification

The existing architecture is unchanged: tenant FK on every business row, ORM auto-scoping and stamping, a signed `tenant_id` JWT claim, and middleware. Verified:

- **Tenant from server-side context only.** A client posting `tenant`, `tenant_id` and an `X-Tenant-Id` header naming another client still creates the row in its own tenant, and the other client cannot see it (`IsolationTests.test_client_supplied_tenant_ids_are_ignored`).
- **Regular client admins cannot reach other clients or the platform.** `/api/superadmin/tenants/`, `summary/`, another tenant's detail, PATCH, `workspace/` and `data/` all return 403. In the browser, the client admin has no Client Management link, typing `#/superadmin/tenants` redirects away, and their token gets 403 from the platform API.
- **Super Admin cross-client access is explicit and audited.** Opening a client's workspace is logged (`WORKSPACE_OPENED`, actor). Data views and exports, backups, invitations issued and used, and every profile, subscription, module, seat, user and branch change are written to `TenantAuditLog` with actor and details. Module, subscription, seat and profile changes are now separate history rows.
- **Existing sweeps still pass** (`tests_tenant_modules`): 161 GET endpoints probed as client B for client A's data, and 165 cross-client detail/PATCH/DELETE calls refused. Branch-isolation and multi-company suites also pass.
- **Module API enforcement — new: reads too.** Previously only writes were gated. Now a module switched off for a client also refuses **direct reads** of the endpoints it owns (403 `module_disabled`):
  - Optical: appointments, eye tests.
  - Wholesale, and Purchase.
  - Each accounting tier's screens.

  Reads stay open only where another module the client has legitimately reads them (New Sale reads eye tests; vouchers read purchase bills and wholesale dealers). Every cross-module reader was mapped from the frontend source before the rules were written.
- Security was not weakened anywhere: no permission was loosened, and `is_platform_admin` / `IsPlatformAdmin` remain the only gate.

## 6. UI size and responsive improvements

All of this is done centrally in `theme/theme.js`, so every page benefits without page rewrites.

- **Density setting**:
  - **Compact** (new default): 6 px spacing unit, 13 px base font.
  - **Comfortable**: 8 px spacing unit, 14 px base font.
  - The toggle is in the header, next to the dark-mode button, and is remembered per browser (`localStorage ui_density`; a blocked storage just means the default). Colours and shapes are identical in both.
- **Typography**: a consistent scale. h4 1.35 rem, h5 1.15 rem, h6 1 rem, body 0.875 / 0.8125 rem (was MUI's 2.125 / 1.5 / 1.25 rem headings). Page-title icons (36 px) now scale with their heading (`1.25em`). Totals and alerts keep their weight and colour.
- **Layout**: sidebar 280 → **232 px** (collapsed 70 → 60), header 64 → **52 px**, navigation rows 44 → 36 px, tighter page, card and dialog padding.
- **Controls**: inputs default to the small size (≈36 px instead of 56 px); buttons 32 px (small 28 px); icons 20 px; chips 22 px; tabs 38 px.
- **Tables**: rows ≈32 px (small) / 36 px, headers bold and compact, pagination toolbar 40 px. The Client Management table drops Company and Modules into secondary text below 1536 px, so every column fits a 1366 px laptop.
- **Modals**: never taller than the window (`calc(100% - 32px)`), with tighter title, content and action padding. The new-client wizard goes full-screen below 700 px.
- **Verified in a real browser** (headless Chrome over CDP, signed in as the client admin): **no page-level horizontal scroll** on Dashboard, New Sale, Orders, Products, Stock Overview, Purchase Entry, Eye Test, Reports, Settings and Users at **1366×768, 1440×900 and 1920×1080** (30 checks), plus Client Management at all three sizes. The wizard fits inside 1366×768. The density toggle changes the sidebar from 232 to 264 px and is remembered.

## 9. Remaining limitations

- **No e-mail delivery.** Setup links are copied and sent by the platform admin. Wiring an SMTP provider is a deployment decision.
- **Role-level read access** is not enforced. Reads are gated by the client's *subscription*; a role's "none" level still hides the module in the UI and blocks writes, but not direct GETs of shared data. Shared masters (products, categories, brands, stock, customers, sales invoices) stay readable by every package because core modules (Reports, Settings → labels and bill designer, Administration → import) read them.
- **No automatic renewal or billing.** Expiry blocks access on the next day; there are no reminders, grace period or payment integration (as instructed).
- **Hosted deployment not touched.** On Render, after deploying, run `manage.py platform_admin_status`. If it reports a blocked account, set `DJANGO_SUPERUSER_*` and run `bootstrap_admin --reset-password` (it only repairs a tenant-#1 account). The local dev DB still has its old `superadmin` account; its password was not changed.
- **Migration `common 0012`** must be applied with the deploy. It is additive and was verified on a fresh database. A running dev `runserver` with `AUTO_MIGRATE` would apply it to the dev DB as soon as it restarts.
- **Density** is per browser, not per user account.
- **Pages with their own hard-coded pixel sizes** inside custom widgets (for example the coloured Rx grid) keep those sizes; they fit at 1366 px but are not scaled by the density switch.
- **ESLint** cannot run: the repo has no `eslint.config.*`, which is pre-existing. The production build was used as the syntax/type gate.
